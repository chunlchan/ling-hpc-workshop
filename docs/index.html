Your first cluster job: counting bigrams

You will ask an AI agent (pi) to write a small Python program and a batch script. Then you check the script, submit the job to Quartz yourself, watch it run, and read the results. It takes about 30 minutes, at your own pace.

When you finish, you can

  • read a SLURM batch script and say what each #SBATCH line asks for
  • submit, monitor and cancel a job
  • find and check the job's output
  • explain why work runs through a scheduler on compute nodes, not on the login machine
  • say what a bigram count is, and read the top bigrams

You need

  • pi installed on Quartz and answering (connected to your LLM service with your API key)
  • access to the workshop allocation, c02318, or an allocation of your own
  • a terminal on Quartz, for example in the Research Desktop

Stuck at any point? Jump to Get help or email cc155@iu.edu.

1

What the job does

3 min

A bigram is a pair of consecutive words. Counting bigrams shows which phrases a text uses most, and bigram counts are the basis of simple language models.

the cat sat on the mat and the cat slept has 10 words, so 9 bigrams (8 distinct):

the cat ×2cat satsat onon the the matmat andand thecat slept

Your job reads 3,999 passages (about 5,000 words each) from Project Gutenberg books, 19.5 million words in all. It counts the word pairs inside each passage, adds them up, prints the 20 most frequent bigrams, and saves the top 1,000 to a file.

About the data. The corpus was downloaded from Project Gutenberg books and cleaned ahead of time (the Gutenberg headers and license text removed), so you don't have to do that. It lives in a folder under /N/project/, which is IU's Slate-Project storage. Slate-Project is the preferred filesystem for computing on Quartz, and it is also a good place to keep your own research data, because it is shared between you, your advisor and anyone on your team.

The linguistics is simple on purpose. The point is the workflow: request resources, check the script, submit, wait, read the results.

Get the prompt and edit it

5 min

The prompt is a text file that tells pi what to write. You will save a copy in your working folder, fill in three values, and remove a short header.

2a. Make a working folder and save the prompt in it as prompt.txt

This folder is where pi will work and write its files. In a terminal, one command makes the folder and downloads the prompt into it:

mkdir -p ~/bigrams && cd ~/bigrams
wget -O prompt.txt https://raw.githubusercontent.com/chunlchan/ling-hpc-workshop/main/AGENT_PROMPT.md

Prefer your browser? Run just the mkdir line, then open the prompt ↗, press Ctrl+S, and save it as prompt.txt inside the bigrams folder.

2b. Open it in a text editor

Use any editor you like. In a terminal, nano works everywhere:

nano ~/bigrams/prompt.txt

In nano: arrow keys move, Ctrl+K deletes the current line, Ctrl+O then Enter saves, Ctrl+X exits.

2c. Replace the three values

In the "My settings" section, replace each <...> including the angle brackets with the values from step 0: <PATH>, <PARTITION> and <ACCOUNT>. (You can leave the text in parentheses after each one.)

2d. Delete the header

At the top of the file is a short "How to use this" header. Delete everything above the --- line, and the --- line itself. Keep everything below it.

✓ Checkpoint Save the file, then run: 
grep -n -E '<PATH>|<PARTITION>|<ACCOUNT>' ~/bigrams/prompt.txt
head -3 ~/bigrams/prompt.txt
The first command should print nothing (no placeholders left). If it prints lines, those values still need replacing. The second should show a blank line, then I'm new to HPC. Please help me write my first job.... If you still see a title or "How to use this", delete the header.
3

Start pi and give it the prompt

5 min
  1. Start pi in your working folder, so the files pi writes land there: 
    cd ~/bigrams
pi
  2. Select the Gemma model. Type /model, press Enter, and choose Gemma with the arrow keys. Check the model name at the bottom of pi's screen. pi goes back to its default model every time it starts and every time you type /new, so do this every time, before you send anything.
  3. Send pi this message. pi reads prompt.txt itself, so there is nothing to copy out of the file: 
    Read prompt.txt in this folder and follow its instructions exactly. I will submit the job myself, so do not run sbatch or the Python script.
    Type it, or paste it (Ctrl+Shift+V; see the copy and paste note in step 0 if you use the web version), then press Enter.
  4. Wait while pi works, usually a minute or two. It may look up Python versions with module spider. It should write two files and then print some commands for you to type, and stop.
Stop pi if it tries to run the job pi is told never to submit or run the job, because you do that. If you see it run sbatch, srun, or python3 bigrams_serial.py, press Esc straight away. Then type /quit, check squeue --me, and cancel anything it submitted with scancel <jobid>. Start again from step 3, and select Gemma again. (See the cheat sheet.)
✓ Checkpoint pi's last message lists commands like sbatch run_bigrams.slurm and then stops. Leave pi with /quit, then check: 
ls ~/bigrams
squeue --me
You should see prompt.txt, bigrams_serial.py and run_bigrams.slurm, and squeue --me should show no jobs yet.
4

Read the batch script

5 min
Stop here: don't submit anything yet A batch script is a request to the scheduler. Reading it before you run it is the most useful habit in this whole exercise, and checking what an AI wrote for you is a habit worth having.

Print the script with line numbers:

cat -n ~/bigrams/run_bigrams.slurm

What each part means

Your script may order the lines differently, but it should contain all of these.

LineWhat it does
#SBATCH --partition=...Which queue to wait in: general (or debug)
#SBATCH --account=...Which allocation is charged for the job
#SBATCH --cpus-per-task=1One CPU core. This is a serial job that uses a single process
#SBATCH --mem=4GMemory limit. The job is killed if it needs more
#SBATCH --time=00:10:00Time limit (hours:minutes:seconds). The job is killed when it runs out
#SBATCH --output / --errorWhere the log files go. %u is your username and %j is the job number
module load python/...Quartz provides software through modules, and a compute node starts without Python loaded
export CORPUS_DIR=...
export OUTPUT_DIR=...		Tell the program where the corpus is (read-only) and where to write its results
python3 bigrams_serial.pyThe actual work: run the program pi wrote

Confirm your script matches what you chose

  • --partition is your partition (general or debug)
  • --account is c02318 (or your own allocation)
  • --cpus-per-task=1, --mem=4G and --time=00:10:00
  • a module load python/... line, and no module purge
  • CORPUS_DIR is the path you put in the prompt, and OUTPUT_DIR is /N/scratch/$USER
  • --output and --error point into /N/scratch/%u/

Test yourself

What happens if the job needs more than 10 minutes? The scheduler stops it, and sacct reports TIMEOUT. The time limit protects the shared cluster from runaway jobs.
Where will you find the job's log? In /N/scratch/$USER/bigrams_<jobid>.out, and any errors in the matching .err file.
Why does the script load Python, when you already have Python in your own terminal? The job runs on a compute node, which starts with a clean environment. Anything the program needs has to be loaded inside the script.

If something is wrong

Don't edit blindly. Start pi again in the same folder (select Gemma again with /model) and tell it exactly what to change, for example:

Please fix run_bigrams.slurm: the --account line should be c02318. Only edit the file. Do not run anything.

Then read the script again. Optional: read the counting loop in cat -n ~/bigrams/bigrams_serial.py and check that it counts pairs within each line only.

✓ CheckpointYou can say what each #SBATCH line asks for, and every box in the checklist is ticked.
5

Dry run, then submit

3 min

5a. Dry run

A dry run asks the scheduler to check your script and the account, without creating a job:

cd ~/bigrams
sbatch --test-only run_bigrams.slurm

If all is well, you get one line like this (your numbers and times will differ):

sbatch: Job 12243972 to start at 2026-10-15T08:47:51 using 1 processors on nodes c70 in partition general

The start time is an estimate of how long you might wait in the queue. No job exists yet: squeue --me still shows nothing.

If something is wrong with the account or partition, you get an error instead, such as:

allocation failure: Invalid account or account/partition combination specified

In that case, fix the --account or --partition line (see step 4) and dry-run again.

5b. Submit

sbatch run_bigrams.slurm
Submitted batch job 12243986

Write down the job number. You will use it in the next steps.

Optional: get an email when the job ends Use this instead of the plain command above (running both would submit the job twice): 
sbatch --mail-type=END,FAIL --mail-user=$USER@iu.edu run_bigrams.slurm
The cluster emails your IU address when the job finishes or fails. It can take a minute and may land in spam. Still use step 6 to watch the job: this job is short.
✓ CheckpointYou saw Submitted batch job ... and wrote down the number.
6

Watch your job

2 to 5 min

Instead of retyping squeue --me, let the terminal refresh it for you every 5 seconds:

watch -n 5 squeue --me

What you will see

Every 5.0s: squeue --me                          Thu Oct 15 08:52:10 2026

             JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
          12243986   general  bigrams    cc155  R       0:23      1 c70
  • The screen clears and redraws every 5 seconds. Between updates, nothing appears to move, so be patient.
  • ST shows the state: PD means waiting in the queue, R means running. The TIME counter goes up while it runs.
  • When the job finishes, its row disappears, leaving only the header line. That means it is done.
  • Press Ctrl+C to stop watching. (Without watch, squeue --me -i 5 does the same.)

A run takes anywhere from about 15 seconds to a minute once it starts. The wait before it starts depends on how busy the cluster is, from seconds to several minutes.

Confirm how it ended

The job vanishing from squeue doesn't tell you whether it worked. Ask the scheduler (use your job number):

sacct -j <jobid> --format=JobID,State,Elapsed,ExitCode
StateMeaning
PENDING / PDWaiting in the queue
RUNNING / RRunning on a compute node
COMPLETEDFinished normally (exit code 0:0)
FAILEDThe program stopped with an error. Read the .err file
TIMEOUTIt ran past its --time limit
OUT_OF_MEMORYIt needed more than its --mem limit (sacct may show it as OUT_OF_ME+)
CANCELLEDSomeone (maybe you) cancelled it (shown as CANCELLED+ or CANCELLED by ...)
Waiting a long time? Look at the last column of squeue --me: Priority or Resources just means the cluster is busy. If you have waited more than about 10 minutes, cancel and try the debug partition (command-line options override the script): 
scancel <jobid>
sbatch --partition=debug run_bigrams.slurm
✓ Checkpointsacct shows COMPLETED with exit code 0:0.

Read your results

3 min

Your results are in your scratch folder:

ls /N/scratch/$USER

Read the log (use your job number):

cat /N/scratch/$USER/bigrams_<jobid>.out

Look at the top of the saved table, and check that the error file is empty. (If you used Plan B, the table is called bigram_counts_serial.tsv.)

head -20 /N/scratch/$USER/bigram_counts.tsv
cat /N/scratch/$USER/bigrams_<jobid>.err
✓ Checkpoint: your numbers should match 
Documents (lines):   3,999
Total bigrams:       19,500,939
Distinct bigrams:    5,306,726
Most frequent:       "of the"  (177,785 times)
Runtime:             about 15 to 60 seconds (it varies)
The layout, the commas and the wording depend on the program pi wrote, but the numbers should be the same.
What if my numbers are different?
What you seeLikely cause
Total near 19,504,898 (about 4,000 too high)The program counted pairs across the line boundaries. Each line is a separate document, so pairs must stay within a line. Ask pi to fix bigrams_serial.py and run again.
Fewer than 3,999 documentsIt didn't read all the files. Check CORPUS_DIR and that all 40 files are there.
Documents or total is 0, or "no .txt files found"Wrong CORPUS_DIR. Check it with ls.
8

Reflect and go further

optional

What you just did

You wrote a request for resources (a batch script), checked it, handed it to a scheduler, and collected the results. The same pattern scales up to much bigger jobs: only the numbers in the #SBATCH lines change.

Questions to think about

  • Look at the 20 most frequent bigrams. What kinds of words do they contain? What would you want to filter out to find more interesting phrases?
  • The program splits words on spaces, so end. and end count as different words. How would that change your results, and how would you fix it?
  • What would change if the corpus were poetry, or a set of legal documents?

Try something else (each one is optional)

  • Break it on purpose. Run the job with far too little memory (a command-line option overrides the script): 
    sbatch --mem=50M run_bigrams.slurm
    It fails within seconds. Check sacct (the state is OUT_OF_ME+, with exit code 0:125) and read the .err file in /N/scratch/$USER: it says the program was Killed by an oom_kill event. That is how a memory limit shows up, and it is the message to look for when a job dies early.
  • Count trigrams (three-word sequences). Start pi in ~/bigrams and ask it to write a new program and batch script. Remember to read the new script before you submit it.
  • Ask pi for a parallel version that uses several CPU cores, and compare the runtimes. More cores are not always proportionally faster. Why might that be?
  • Open the results table (/N/scratch/$USER/bigram_counts.tsv) in a spreadsheet.

Email me

Write to cc155@iu.edu. Say which step you are on and what you expected, and paste the error message. Then run this one command, which collects what I need into a single file, and paste or attach ~/help_info.txt:

{ echo "== when"; date; echo; echo "== my jobs now"; squeue --me; echo; echo "== recent jobs"; sacct -X --starttime=today --format=JobID,JobName,Partition,Account,State,Elapsed,ExitCode; echo; echo "== batch script"; cat ~/bigrams/run_bigrams.slurm; echo; echo "== newest error file"; cat "$(ls -t /N/scratch/$USER/bigrams_*.err 2>/dev/null | head -1)" 2>&1; echo; echo "== newest output file"; cat "$(ls -t /N/scratch/$USER/bigrams_*.out 2>/dev/null | head -1)" 2>&1; } > ~/help_info.txt 2>&1; echo "Saved ~/help_info.txt"

It contains your job list, batch script and log files, and never your API key.

Plan B: use a known-good script

If pi's script still doesn't work after a couple of tries, use this tested pair and carry on from step 5 (it is set up for the workshop allocation and the general partition; edit the account or partition lines if yours differ):

mkdir -p ~/bigrams_planb && cd ~/bigrams_planb
wget -O bigrams_serial.py https://raw.githubusercontent.com/chunlchan/ling-hpc-workshop/main/reference/bigrams_serial.py

With Plan B, the results table is saved as bigram_counts_serial.tsv (not bigram_counts.tsv), and the log lines read "Documents (lines)" and "Finished in".

If you can't read the corpus folder

Permission denied, folder not found, or very slow? Download your own copy, then use the path it prints as the corpus folder (in the prompt, or in the script's CORPUS_DIR line):

mkdir -p ~/ling_corpus && cd ~/ling_corpus
wget https://github.com/chunlchan/ling-hpc-workshop/releases/download/2026-10-12_01/prepared_4k_concat.zip
unzip prepared_4k_concat.zip
ls prepared_4k_concat | wc -l
echo $PWD/prepared_4k_concat

The wc -l line should print 40. The last line prints the path to use.
